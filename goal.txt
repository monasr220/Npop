# Npop — Full-Stack Frontend, UX, Architecture & Security Specification

## 1. Project Vision

Npop is a Music Social Network that combines music streaming, artist publishing, and social interaction.

It is a platform where:
- Listeners discover, listen to, rate, and discuss music.
- Artists publish music, manage albums, and build communities.
- Users interact through posts, comments, ratings, playlists, and following.

The objective is to build a complete, production-oriented application with a professional interface, organized architecture, strong security, and comprehensive documentation.

This is not a simple UI project. Treat it as a real software product.

# 3. Brand Identity & Three Primary Colors

Npop must have a recognizable visual identity.

Use exactly three primary brand colors across the application.

The colors should communicate:
- Music culture and creativity.
- Confidence and identity.
- A strong social community.
- A distinctive editorial aesthetic.

### Primary palette

<escape>
1. WARM BEIGE — #E8DCC8
2. DEEP RED — #B3262D
3. MATTE BLACK — #171717
</escape>

These are the three primary brand colors.

### Color roles

**Warm Beige — #E8DCC8**
- Main light-theme background.
- Secondary surfaces, content areas, cards and reading surfaces.

**Deep Red — #B3262D**
- Primary brand accent, main action buttons and active navigation.
- Likes, social interactions, highlights and selected states.

**Matte Black — #171717**
- Main dark-theme background.
- Typography on light surfaces, navigation and strong contrast.

Supporting neutral shades derived from the three colors are allowed for borders,
muted text, disabled elements, secondary backgrounds and subtle separators.
Do not introduce additional competing brand colors.

### Visual direction

The design should communicate music culture, creativity, confidence, identity,
a strong social community and a distinctive editorial aesthetic. Avoid a generic
corporate-dashboard look.

### Light theme

Warm beige is the dominant background, matte black carries typography and deep
red marks important interactions. The result should feel warm, clean, elegant
and comfortable for extended browsing.

### Dark theme

Matte black is the dominant background with slightly lighter neutral surfaces,
beige typography and deep red for important interactions. Avoid pure black
everywhere; use subtle surface variations for hierarchy.

### Design rules

- Keep color usage consistent across all pages.
- Red is an accent, not the dominant background.
- Beige provides warmth and reduces harsh contrast.
- Black establishes structure and readability.
- Do not use all three colors equally in every component.
- Maintain WCAG AA contrast wherever applicable and test both themes
  independently.
- Define colors centrally using CSS variables or Tailwind design tokens.
- Do not use random gradients or excessive shadows.

# 5. User Types — Listener vs Artist

This distinction is a fundamental part of Npop.

Do not treat every user as having the same experience.

The application must clearly distinguish between a Listener and an Artist.

## Listener Experience

A Listener is someone who primarily consumes and interacts with music.

The Listener should have access to:

- Music discovery.
- Music playback.
- Artist discovery.
- Album browsing.
- Social feed.
- Creating posts.
- Commenting.
- Rating posts.
- Liking and sharing.
- Following artists and users.
- Creating playlists.
- Managing favorites.
- Listening history.
- Personal profile.
- Notifications.

The Listener should not see artist-only management tools.

## Artist Experience

An Artist is a user who publishes and manages music.

An Artist has all Listener capabilities, plus:

- Artist profile.
- Artist dashboard.
- Music upload.
- Album creation.
- Track management.
- Album artwork management.
- Published music management.
- Artist-specific statistics.
- Audience and follower information.

Artist-specific navigation should include:

- Artist Dashboard.
- My Music.
- My Albums.
- Upload Track.
- Manage Profile.

### Role-specific UX

The UI should adapt based on the authenticated user's actual role.

Examples:

**Listener**
- Discover Music.
- Your Playlists.
- Your Favorites.
- Listening History.

**Artist**
- Artist Studio.
- Your Discography.
- Upload Music.
- Manage Albums.
- Audience Overview.

Do not simply hide or display buttons.

The navigation, dashboard, and relevant user workflows should reflect the user's role.

### Important authorization rules

- Only authorized artists can upload tracks.
- Artists can only manage their own content.
- Regular users cannot access artist management endpoints.
- Users cannot modify another user's profile or resources without permission.
- Admin permissions must be separate.

Frontend role checks are for UX only. The backend must enforce all permissions independently.

Do not invent a role-conversion or artist-registration process if the existing backend does not support it. Identify what is missing and propose the necessary backend implementation.

# 8. Security — Production-Oriented Security Requirements

Security must be treated as a core engineering requirement.

Do not consider a project secure merely because it uses JWT.

Perform a security audit of the existing backend and fix identified vulnerabilities.

## 8.1 Authentication Security

- Secure password hashing using Argon2id or a properly configured bcrypt implementation.
- Never store plaintext passwords.
- Validate credentials.
- Implement appropriate access-token expiration.
- Use secure refresh-token handling if supported or implement it properly.
- Revoke or invalidate sessions where appropriate.
- Protect against brute-force login attempts.
- Avoid revealing whether a particular email address exists during authentication.
- Protect sensitive authentication endpoints.

Do not invent a refresh-token endpoint without implementing and testing its backend functionality.

## 8.2 Authorization

Implement server-side authorization for every protected operation.

Prevent:

- Unauthorized access to private resources.
- IDOR vulnerabilities.
- Users modifying other users' content.
- Artists modifying another artist's music.
- Regular users accessing administrative functions.
- Unauthorized file access.

Always verify resource ownership on the backend.

## 8.3 Rate Limiting

Implement real server-side Rate Limiting.

Do not implement rate limiting only in React.

Use an appropriate backend solution such as SlowAPI or another maintained rate-limiting library.

Configure limits according to endpoint sensitivity.

Suggested initial policy:

| Endpoint category | Suggested limit |
|---|---|
| Login | 5 attempts / minute / IP |
| Registration | 5 requests / hour / IP |
| Password reset | 3 requests / hour / IP |
| Comments and posts | 30 requests / minute / user |
| Search | 60 requests / minute / user |
| Music upload | 5 requests / hour / artist |
| General API | 120 requests / minute / user or IP |

These are initial configuration values, not universal limits. Adjust them according to expected traffic and testing.

Requirements:

- Return HTTP 429 when limits are exceeded.
- Include appropriate retry information.
- Apply stricter limits to sensitive operations.
- Consider both IP and authenticated user identity.
- Use a shared storage backend such as Redis when deploying multiple workers or instances.
- Avoid trusting spoofable forwarded IP headers.
- Document all rate limits.

## 8.4 Input Validation

- Validate all incoming request data.
- Use Pydantic schemas.
- Apply length limits.
- Validate IDs and query parameters.
- Validate uploaded files.
- Prevent unexpected file types.
- Prevent excessively large requests.
- Sanitize or safely render user-generated content.

Never trust client-side validation alone.

## 8.5 XSS Protection

Protect against Cross-Site Scripting.

- Escape user-generated content.
- Avoid dangerous HTML rendering.
- Sanitize rich-text content if supported.
- Use safe rendering practices.
- Configure a suitable Content Security Policy.

Pay particular attention to posts, comments, biographies, and profile information.

## 8.6 SQL Injection Protection

- Use SQLAlchemy parameterized operations.
- Avoid unsafe raw SQL.
- Validate dynamic sorting and filtering parameters.
- Never concatenate untrusted input into SQL queries.

## 8.7 CSRF Protection

If authentication uses cookies:

- Configure appropriate SameSite behavior.
- Enable Secure and HttpOnly flags.
- Implement CSRF protection for state-changing operations where required.

If using Bearer tokens in authorization headers, evaluate the actual browser storage and request model rather than blindly applying cookie-based assumptions.

## 8.8 File Upload Security

Music and image uploads require special attention.

Implement:

- File size limits.
- Allowed extensions.
- MIME-type validation.
- File signature validation where applicable.
- Safe filenames.
- Upload authorization.
- Ownership validation.
- Storage isolation.
- Safe deletion behavior.

Do not trust filenames or MIME types provided by the browser.

Keep Cloudinary credentials on the backend.

Use secure server-side upload flows or properly restricted signed uploads.

Do not expose Cloudinary API secrets in frontend code.

## 8.9 HTTP Security

Configure suitable HTTP security headers:

- Content-Security-Policy.
- X-Content-Type-Options.
- Referrer-Policy.
- Strict-Transport-Security in HTTPS production environments.
- Appropriate frame protection.

Configure CORS with explicit trusted origins.

Do not use unrestricted wildcard origins with credentialed requests.

Use HTTPS in production.

## 8.10 Secrets and Environment Variables

- Keep credentials in environment variables.
- Never commit `.env` files.
- Provide a sanitized `.env.example`.
- Validate required configuration at startup.
- Separate development and production settings.
- Never expose secrets through API responses or logs.

## 8.11 Database Security and Reliability

- Use database constraints.
- Use transactions where appropriate.
- Avoid unsafe cascade behavior.
- Add indexes to frequently queried fields.
- Use proper migration management with Alembic if needed.
- Configure database backups.
- Test restore procedures.

If deploying with multiple workers, ensure the database configuration supports concurrent production usage. Do not assume SQLite is suitable for every deployment scenario.

## 8.12 Logging and Monitoring

- Use structured logging.
- Log important security events.
- Log authentication failures without logging passwords or tokens.
- Record relevant administrative actions.
- Monitor unexpected errors.
- Avoid exposing internal tracebacks to users.
- Add health-check endpoints where appropriate.

## 8.13 Dependency Security

- Audit Python dependencies.
- Audit frontend dependencies.
- Remove unnecessary packages.
- Pin or manage dependency versions appropriately.
- Review known vulnerabilities.
- Avoid abandoned libraries.

### Security completion requirement

Produce a security checklist documenting:

- Implemented protections.
- Tested protections.
- Remaining vulnerabilities.
- Known limitations.
- Deployment recommendations.

Do not claim the system is fully secure without actual verification.

## Naming Conventions

Python:
- `snake_case` for files, variables, and functions.
- `PascalCase` for classes.

React / TypeScript:
- `PascalCase` for React component files and components.
- `camelCase` for functions and variables.
- `kebab-case` or consistent domain-based naming for non-component assets.
- Clear names for API services, hooks, and types.

Examples:

Avoid:
- `test2.py`
- `new_final.py`
- `userStuff.ts`
- `data1.ts`
- `temp.jsx`

Prefer:
- `user_service.py`
- `artist_dashboard.tsx`
- `track_api.ts`
- `use_current_user.ts`
- `playlist_schema.py`

- Avoid oversized modules.

- Keep naming consistent.
- Avoid unnecessary abstractions.
- Preserve existing functionality.
- Update every import after renaming.
- Update configuration paths.
- Update tests.
- Update documentation.

Before deleting or renaming anything, check whether it is referenced elsewhere.

Do not delete files just because their names appear unusual.
